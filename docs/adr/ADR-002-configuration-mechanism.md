# ADR-002 — Configuration mechanism: Kustomize over Helm

> [!info] Status
> **Accepted.** Revisit if this is ever packaged for someone else to install with their own values. That's the condition under which Helm's templating starts earning its keep, and it's precisely the condition this repository doesn't have.

## Context

There are two deployment modes — a development one with the source mounted and a production-shaped one with the source in the image — and they differ in a handful of specific ways: the image tag, where `/app` comes from, whether the root filesystem is read-only, and how many replicas run. Everything else is shared.

That's a small, structured difference between two variants of one thing. The question is which tool expresses it with the least machinery between the manifest and what is applied.

There's also a self-imposed constraint: *one configuration mechanism, not two*. Whatever is chosen has to cover the whole surface, because a repository where some things are Helm values and some are Kustomize patches is worse than either.

## Decision

Use **Kustomize**, through `kubectl apply -k` and `kubectl kustomize`. A base under `k8s/base/` and two overlays under `k8s/overlays/{dev,prod-shaped}/`.

Use `configMapGenerator` for every ConfigMap, with the name-suffix hash left **on**.

Install no additional binary for it: `kubectl` has Kustomize built in, so the tool count stays at two.

## Alternatives

### Helm

**Advantages** — Templating handles cases a strategic-merge patch cannot express at all, such as generating N consumer Deployments from a list rather than writing six near-identical blocks. Real lifecycle hooks, which would make the `setup:upgrade` ordering in `scripts/deploy.sh` a `pre-install,pre-upgrade` annotation instead of a script step. `helm rollback`. It's also what most shops actually run, so it's the more transferable skill.

**Disadvantages** — A third binary. A templating layer between the file and the object, which means the thing in the repository is not the thing applied — and when the point is to see plainly what Kubernetes is doing, that indirection is a cost paid on every read. Values files reproduce the overlay structure with more ceremony. And the case Helm is best at — packaging something for other people to install with their own values — is explicitly not this.

### Plain YAML, one directory per environment

**Advantages** — Nothing between the file and the cluster. Every manifest is exactly what gets applied.

**Disadvantages** — Two full copies of thirty-odd objects, differing in four fields, drifting from the first week. This is the option the overlay structure exists to avoid.

> [!important] Helm was the near miss, and the loop-over-a-list gap is real
> `jobs/consumers.yaml` is six near-identical Deployments that Helm would generate from a six-item list, and that file is the concrete cost of this decision — it's generated by a script in this repository rather than by the deployment tool. That cost was accepted because the alternative puts a template engine between every manifest and the cluster, everywhere, to save repetition in one file. If a second file develops the same shape, revisit.

## Consequences

- **`setup:upgrade` ordering has to live in a script**, because Kustomize has no hooks. `scripts/deploy.sh` renders the overlay, splits the Job out, applies everything else, waits for the data tier, then applies the Job. That's a hook written by hand, and it's honest about being one.
- **The ConfigMap name-suffix hash is kept on, deliberately.** A changed VCL or a changed consumer list produces a new ConfigMap name, which rolls the pods that mount it. Disabling the hash — which many repositories do, to keep names tidy — reintroduces the single most expensive hour in Kubernetes: *"I changed the config, applied it, and nothing happened."*
- **The consumer Deployments are generated by a script, not by the deployment tool.** Regenerating them means re-running that script, and nothing enforces that the file matches it. `make verify-consumers` catches the mismatch that actually matters; it doesn't catch this one.
- **No `helm rollback`.** Rolling back is `git revert` plus `make deploy`, which in an immutable-image model is the same operation as any other deploy.
